# MyBarPool Architecture

How the program, the keeper and the clients fit together, and why each rule is the way it is. This is the design the program is being built from; where the program and this document disagree once code exists, the program is the truth and this document gets fixed.

## Game rules

### Games
- Every NFL game on the schedule is playable: all 272 regular-season games across Weeks 1–18 (Thursday, Sunday, Monday and the odd Saturday or holiday slot) and every postseason game through the Super Bowl. Boxes are best known as a Super Bowl tradition, and that Sunday will be the biggest day of the year, but the product is built for the other 21 weeks too; a bar that runs a board on every Sunday game is the design target, not the exception.
- The scores service publishes the season schedule (from the same sources it uses for scores) and creates the per-game record when a game is first scheduled, so pools can be created as soon as a week's kickoff times are known, typically several days ahead. There is no horizon limit: once a game record exists a pool can be opened on it, even months out; the 3-open-pools cap is what stops the list filling with distant games. Ordinary schedule changes announced by the league ahead of time (flex scheduling, a moved kickoff slot) update the game record and every pool on it; a postponement is not a schedule change but a return (see Returns and splits).
- Preseason is off at launch and is a config switch, not a program change. International and neutral-site games are ordinary games.
- A game is identified on-chain by a canonical game key (season, week, home team, away team; see PROGRAM.md), not by any source's ID, so the record depends on no vendor's numbering; the mapping from each source's IDs (ESPN's event ID, Kalshi's milestone ID, and the Sportradar game ID that both the Polymarket stream and Kalshi's milestones carry) to that key lives in `packages/shared` so the keeper, the app and third-party clients agree on which game a pool is on. The on-chain game record is a PDA seeded by that key *and* the scheduled kickoff (Unix seconds), so a rescheduled game, which keeps its key but gets a new time, gets a distinct record: the old one stays marked postponed with its pools returned, and the new one is a fresh record that pools can be created on. The record stores the scheduled kickoff it was seeded with (which is what the 30-day reclaim clock and the 72-hour update bound are measured from) and, separately, the current recorded kickoff that the keeper may update.

### Grid
- 5×5 = 25 boxes. Columns = home team, rows = away team.
- Digits 0–9 are shuffled onto each axis independently, two digits per row/column (positions i and i+5 share a lane).
- Each box covers 4 of the 100 possible last-digit pairs, so every box has a 4% chance per quarter and a full grid always produces a winner.
- Naming: the word is **box**, which is what bars call them. It is used consistently in everything a person sees and in all code: UI copy, notifications, program instructions and account fields (`box_count`, `boxes`), events, API responses, keeper logs, and component names. The game's other common name is not used anywhere in the product or codebase; the one exception is the README's opening line, which uses it once so people searching for the game find it.

### Buying
- Any wallet can buy any number of boxes in any number of pools. The one exception is a pool's creator, who is capped at 5 boxes in their own pool (see Limits below).
- Nobody picks a box. The buy instruction takes a count, and the program assigns boxes from those still available. Because digits are drawn after the grid sells out, every box is identical before the draw (4% per quarter), so choosing was never a real choice. Assignment removes collisions ("box already taken" after signing), makes multi-buy one signature, and simplifies the program.
- Assignment must look random. Boxes are chosen by shuffling the remaining set with a seed from the most recent entry in the SlotHashes sysvar mixed with the buyer's key and the pool's sale count, so three boxes bought together land scattered across the grid, never 1-2-3. Predictability is harmless here since positions carry no value; Entropy is reserved for the digit draw.
- Buyers see their wallet on their assigned boxes immediately after purchase (the short address, or its `.skr` name if one resolves; the connected wallet reads YOU). Box ownership is the on-chain `owners` array, so the grid, the activity list and a wallet's history are all read from the chain, with every purchase, payout and return linked to its transaction signature.
- Numbering: boxes are labelled 1–25 everywhere a person sees them (frontend, notifications, keeper logs, on-chain events, API responses). The program may store a 0-based index internally, but the conversion happens once in `packages/shared` and nothing user-facing ever shows 0–24. Box 1 is top-left, numbering runs left to right, then down.
- Sales close at the pool's recorded kickoff. That starts as the scheduled kickoff and follows ordinary league schedule changes (flex scheduling, a moved slot on the same weekend) when the score sources agree on the new time before the game (same agreement rule as scores, see Score integrity); an Open pool keeps selling until the recorded kickoff and the unfilled return fires at that moment. It does not follow a postponement: a game that isn't played at its scheduled time is returned, never carried to a new date (see Returns and splits).
- Kickoff updates, precisely. The recorded kickoff lives on the per-game record, so one keeper transaction moves every pool on the game. All times are Unix seconds compared against the Clock sysvar. `update_kickoff(new_time)` is accepted only if all of: `now < recorded_kickoff` (sales are still open; a kickoff that has passed can't be moved), `new_time > now`, and `scheduled_kickoff − 72h ≤ new_time ≤ scheduled_kickoff + 72h`. Earlier and later moves are both allowed within those bounds (the lower one from the 2026-10-23 audit: without it a keeper could have set kickoff to a second from now and locked a pool mid-sale). `buy` requires `now < recorded_kickoff`; `return_unfilled` requires `now ≥ recorded_kickoff`. Because an update can only land while `now < recorded_kickoff` and always sets a time in the future, and a return can only land once `now ≥ recorded_kickoff`, the two can never both be valid in the same slot: whichever the cluster orders first wins and the other fails cleanly, with no window in which a pool is both returned and still selling.
- Box price: each token has a minimum, a step, and a maximum in platform config. The program rejects any price that isn't `min + k × step` within the cap. Initial values (adjusted by the admin as token prices move, no program upgrade needed):

| Token | Min | Step | Max per box | Smallest / largest pool |
|---|---|---|---|---|
| SOL | 0.05 | 0.05 | 1 | 1.25 / 25 SOL |
| SKR | 100 | 100 | 5,000 | 2,500 / 125,000 SKR |
| ORE | 0.05 | 0.05 | 1 | 1.25 / 25 ORE |

- The per-box cap also bounds the damage of any single wrong-score incident; it may be raised once the keeper has a track record.
- Box prices display in each token's natural precision: SKR as whole numbers, SOL and ORE to two decimals; the price ladder guarantees this is exact. Prizes and fees are shown to at most four decimals, rounded half-up for display only (a 25/25/25/25 quarter on the smallest SOL pool is 0.28125 SOL and displays as 0.2813; the transaction carries the exact amount).

### Lifecycle
1. Open — creator picks an NFL game, token (SOL / SKR / ORE), box price and payout split. The creator's 5% share is automatic and part of the 10% base fee; optionally they add up to 5% more on top (the add-on, default 0). Players buy boxes; funds go to a program-owned vault. Any wallet may also add to the prize pool while sales are open (see Sponsorship); nothing is taken from that.
2. Locked — only when all 25 boxes are sold. Every quarter therefore has exactly one winning box that belongs to a player, so there is no rollover logic.
3. Numbers drawn — randomness (see below) assigns digits to both axes.
4. Live — after each quarter ends, the keeper posts the official score on-chain and the program pays that quarter's winner immediately. No dispute window. Platform and creator fees are taken in the first settlement transaction, never before. The Q4 prize is paid when the game is final (see Payouts).
5. Settled — all four quarters paid.
6. Returned — the pool never locked, the game was postponed or cancelled, or the multisig cancelled the pool (draw failure); every buyer's full purchase is sent back to their wallet, and every sponsorship goes back to its sponsor.
7. Split — the game was suspended and not finished; every unpaid prize is split equally across all 25 boxes.
8. Unresolved after 30 days — the pool is still unresolved 30 days after the game's original scheduled kickoff, a state a running keeper never allows; the program lets buyers take their own share back directly (see below).

### Returns and splits
All returns and splits are decided and executed by the platform. No player, creator, or third party can trigger them, with one narrow exception for abandoned pools described at the end of this section.
- Unfilled at kickoff: the keeper returns each buyer's full purchase to their wallet. No fees are taken and players don't have to do anything. Sponsorships on the pool go back to their sponsors in the same pass (see Sponsorship); every return path below that fires before the first settlement does the same.
- Delayed game (weather, lightning, a late start on the same day): Locked pools stay locked and wait; if the delay is announced before kickoff, the keeper posts the later same-day kickoff and Open pools keep selling until then. The line between a delay and a postponement is the league's: a game the feeds report as delayed is played that day; a game they report as postponed is not, and is returned.
- Postponed or cancelled game, verified under the same source-agreement rule as scores: the platform admin (multisig) marks the game postponed or cancelled on the per-game record, one transaction that covers every pool on it, and the keeper then returns every purchase pool by pool, even if a pool had locked. A postponed game is treated exactly like a cancelled one: nobody's money is held for days or weeks waiting on a new date. The rescheduled game gets a new game record with a new kickoff, and creators open fresh pools on it; `create_pool` on a record marked postponed or cancelled always fails. No fee leaves the vault until a prize is paid, so a return is always the full purchase price and the creator earns nothing on a game that didn't happen.
- Suspended game (stopped during or after any quarter and not finished): every prize not yet paid, including the quarter in progress, is split equally across all 25 boxes and sent to their owners. The admin marks the game suspended on the per-game record; the keeper executes the split for each pool. Before the first settlement this is the same as a full return (no fee has been taken, and sponsorships go back to their sponsors); after it, the fee stays taken, sponsorships stay in the prize pool, and only the unpaid prize pool is split.
- Ambiguous game status (sources disagree, or an unfamiliar status): the pool stays locked and the keeper alerts the team. Waiting is always the safe default because funds never leave the vault without a decision.
- Cost: a return is one or two transactions for the whole pool (many transfers per transaction), paid by the keeper. Buyers pay nothing to be returned.

The one exception to platform-only control is the 30-day reclaim, a guarantee written into the program that no pool can stay unresolved indefinitely:
- Condition: the pool is not settled, and the current time is at least 30 days past the game's original scheduled kickoff as stored on the game record (never the keeper-updated kickoff). Nothing else can satisfy it. A pool the keeper had already moved to returned or split but never finished paying is covered by the same clock: each owner takes what the pool already owes them, at the amount it already fixed, and such a pool is not counted as abandoned (its rent still goes to the platform at close). A working keeper pays each quarter within minutes of it ending, returns unfilled pools at kickoff, and closes every pool the same day; the league resolves suspended games within days. Team policy is that no pool is ever deliberately left unresolved past 30 days; any pool still open a month after kickoff is by definition one nobody is operating, and its buyers can reclaim without asking.
- Action: `reclaim` is permissionless per buyer. For a pool that never paid a prize (Open or Locked), each box returns its purchase price. For a pool that has paid some prizes, the pool account tracks `unpaid_prize_pool`, and each box returns `unpaid_prize_pool / 25`, the same arithmetic as a split. Fees already taken stay taken; fees not yet taken are never taken, and the creator earns nothing. Sponsorships follow the same line: on a pool that never paid a prize each sponsor reclaims their own sponsorship in full (`reclaim_sponsorship`, permissionless, same 30-day condition); on a pool that has paid some prizes the sponsorship is already part of `unpaid_prize_pool` and goes to the boxes. Once every box (and, where applicable, every sponsorship) is reclaimed, anyone can close the pool; the pool and vault rent and any rounding dust left in the vault go to the creator, since a pool can only reach that state if the platform is no longer resolving pools (the per-creator counter is separate and closes to the platform as always; see Pool creation).
- What it is not: an outage safeguard. An outage lasting hours delays settlement by hours and the keeper then catches up; the floors and ordering rules are unaffected. Thirty days is far past anything infrastructure can cause. The guarantee exists so that funds in the program are the program's promise, not the operator's, which is what integrators, auditors and store reviewers ask for first.

### Pool creation
- Creation fee: the creator pays the rent for the pool account, the vault, and (first time per game) the open-pool counter, about 0.010 SOL in total (pool ~0.008, SPL vault ~0.0015, counter ~0.001). Where that rent goes when the accounts close is one rule with one exception. The rule: pool and vault rent go to the platform when the pool closes in any outcome, and the counter's rent goes to the platform when the counter closes at zero open pools (the counter is per creator per game, so it outlives any one pool). The exception: a pool closed after an abandoned-pool reclaim sends the pool and vault rent, and any rounding dust in the vault, to the creator, since a pool can only reach that state if the platform is no longer resolving pools; the counter still closes to the platform, because the counter is a shared account and its rent was never tied to one pool. It is a creation fee, not a deposit, and the app labels it as one ("Creation fee 0.010 SOL, covers account rent"), never as a deposit.
- Why the platform keeps it: it is simpler than a refund path, it covers the keeper's transaction costs on pools that never earn a fee, and the creator's 5% share (below) is set high enough that the fee is small next to what a filled pool pays. A creator whose pool doesn't fill loses the creation fee and nothing else.
- Keep the pool account small, since rent is the creation fee: box owners (25 × 32 bytes) dominate; settlement records store quarter, box index and amount (the score is read from the per-game record and the wallet is the box owner at settle time); the emitted event carries the full detail (quarter, score, winning box, wallet, amount). Everything else is fixed-width with reserved padding. Target about 1.4 KB, which keeps the fee at about 0.010 SOL.
- The creator may buy boxes in the same transaction as creating the pool (the create flow's stepper starts at 1 and runs 0–5), so rent and any boxes are one signature. Buying is optional: a bar can run a board without betting in it. The creator's boxes are ordinary boxes: they are among the 25, paid at full price into the pot, assigned at random like everyone else's, and the creator's 5% is computed on the whole pot including their own purchases.
- Creator expectation: a box returns 90% of its price on average, so a 0.05 SOL box is a 0.005 SOL expected loss, while the 5% share of a 1.25 SOL pot is 0.0625 SOL, against a creation fee of about 0.010 SOL. A creator who fills the smallest pool without buying in nets about 0.052 SOL (0.0625 − 0.010); one who also holds 5 boxes nets about 0.027 SOL in expectation (5 × 0.005 expected loss on top). A creator whose pool doesn't fill is out the creation fee only.

### Limits
- Open pools: a wallet may have at most 3 open (unfilled) pools per game. Locked, settled, returned, and split pools don't count, so a creator who fills a pool can open another. A bar can still run a pool on every game of the week.
- Creator boxes: a creator may own at most 5 boxes in a pool they created, counted across the create transaction and any later buys. Other wallets have no per-pool or cross-pool limit; a player can buy into as many pools as they like.
- Both limits are values in platform config, with an optional per-wallet override account (PDA seeded by the wallet) that the admin can create to raise or lower either number for one creator. The program reads the override if it exists, else the config. Changing either is an admin transaction, no program upgrade.
- Why: the open-pool cap stops list clutter, since an unfilled pool costs its creator only the small creation fee. The box cap keeps a creator from stuffing their own grid to make it look nearly full, and keeps the creator's overall expectation positive: at the 10% base fee a creator's break-even is 12.5 boxes before the creation fee (5% × 25 ÷ 10%), about 10 boxes once the fee is counted at 0.05 SOL, so at 5 or fewer, buying in never costs them money in expectation.
- What these limits are not: a security boundary. Self-buying isn't an exploit. A creator who bought all 25 boxes would pay the platform 5% to play against themselves; every box is worth the same before the draw, so buying early gives no edge; and the return on an unfilled pool goes to every buyer, not just the creator. Someone determined to hold more boxes can use a second wallet, and the outcome is the same as if they'd bought them as a player.

### Sponsorship
A pool's prizes are normally the pot minus the fee. Sponsorship is the one way money enters a pool that isn't a box purchase: any wallet can add to a pool's prize pool, and the addition goes to the winners in full.
- Who and when: any wallet, on any pool, while `now < recorded_kickoff` (the same window as `buy`), in the Open, Locked or Drawn state (a full pool is usually drawn well before kickoff and can still be sponsored). The creator can sponsor their own pool through the same instruction, but nothing about creating a pool asks them to; the creator's 5% is fixed and is not traded against sponsoring. The platform never sponsors a pool, including the ones it creates.
- What it is for: a company that wants its name on a game, an ORE community member putting ORE on the ORE pools, a sponsor of a bar's board. It is not expected to be common, and nothing in the app pushes a player towards it. The point is that when someone wants to do it the money and the credit are both handled on-chain.
- No fee: `platform_fee`, `creator_fee` and `integrator_fee` are computed on the pot `P = 25 × price` only. `sponsored_total` is added to the prize pool after fees (see Fees), so a sponsor's whole amount is paid out to winners and the sponsor is never charged for adding it.
- Same token as the pool. An ORE prize on a SOL pool would need a second vault and two transfers per quarter; a sponsor who wants to give ORE sponsors an ORE pool.
- Limits: each `sponsor` call is at least one box price, so dust can't create accounts for nothing; `sponsored_total` per pool is capped at a per-token value in platform config, initially the largest possible pot (25 SOL / 125,000 SKR / 25 ORE), so a sponsorship can at most double the largest pool and the bound on any single wrong-score incident (see Buying, per-box cap) stays meaningful. Adjustable by the admin, no program upgrade.
- Accounts: one `Sponsorship` PDA per (pool, sponsor wallet), created by the first `sponsor` call from that wallet and topped up by later ones, holding the wallet and the cumulative amount; the sponsor pays its rent (about 0.001 SOL) and gets the rent back when the account closes. The pool stores `sponsored_total` and `sponsor_count`. A per-sponsor account, rather than an event alone, is what lets the program return the money to the right wallet without trusting the keeper for the destination.
- Committed at the first settlement, exactly like fees: until the pool pays its first prize, every return path (unfilled at kickoff, postponed, cancelled, draw failure, suspended before the first settlement) sends each sponsorship back to its sponsor in full in the same keeper pass as the box returns, and closes the account with its rent to the sponsor. After the first prize is paid the sponsorship belongs to the pool: a game suspended later splits the unpaid prize pool, sponsorship included, across the 25 boxes, and the sponsor gets nothing back. Abandoned-pool reclaim follows the same split (see Returns and splits).
- Prizes: `quarter_prize[q]` is computed from the full prize pool, so a sponsorship is spread across the quarters in the pool's payout preset rather than landing on one quarter. On a Q4 100% pool it all goes to the final.
- Attribution: the chain records the wallet and the amount, nothing else, and a `Sponsored` event is emitted for every call. Display names, logos and links come from a sponsor directory in `packages/shared`, a reviewed list maintained by the platform, so nobody can put arbitrary text, an image or a link on a pool page for the price of a sponsorship. A wallet not in the directory is shown by its .skr name or a shortened address ("Sponsored by 7kq2…9a3f"), which is still true and still verifiable. Third-party clients see the same wallet and amount in the event and show what they like.
- Directory entry: wallet, display name, logo, website (`https` only) and, optionally, the Android package name of the sponsor's Seeker app, from which the client forms the dApp Store deep link (`solanadappstore://details?id=<package>`, the scheme Solana Mobile documents). That is the whole sponsor benefit beyond the prize: their name and logo on the pool, the card, the link preview, the saved grid image and the printed board, and a tap-through to their site or their app. Links are only ever rendered from the directory, never from anything on-chain; they open in the browser or the dApp Store, never inside the app; nothing is appended to them. Being listed is at the platform's discretion, because the listing is on the platform's surfaces; the on-chain sponsorship is free and permissionless either way.
- Headline (2026-10-22): when a pool has several sponsors, the one named first — on the pool's line ("Sponsored by X and 2 others"), in the link preview, the saved image and the printed board — is chosen by one rule on every surface: directory-listed sponsors before unlisted wallets, then the earlier first sponsorship (the slot of the wallet's first `Sponsored` or `BoxSponsored` event, not its latest top-up), then the wallet string. Amount never orders, so a signed sponsor's name does not move off a board that has already been printed when a later wallet adds one more box price, and an unlisted wallet never headlines over a listed one. The scores service orders the `pool` body this way (`api/views.ts`) and the app applies the same rule on its chain path (`pool-derive.ts`); the function moves into the shared package at the next re-vendor. The sheet lists sponsors in the same order with their amounts. The directory itself has two copies: the service's reviewed list, which a hosted build reads from the `pool` body and which is live after a service deploy, and the bundled list in the shared package, which the app falls back to and which the chain-only path has alone; a new sponsor is therefore named on dev and production within the hour, and in the store build at its next release.
- Why no fee on the sponsorship itself: the whole point to a sponsor, and the whole point to the winners, is that what goes in is what comes out. A cut of a donated prize reads as exactly that, and it would add a second fee flow (per `sponsor` call, before the first settlement) to a fee model that is otherwise one transfer at one moment. If sponsorship ever needs to pay for itself, the directory listing is where that relationship lives, off-chain, and the program doesn't change.
- A sponsor is not a player: a sponsorship is not a box, has no odds and can't win. A sponsor wallet may also buy boxes; the two are separate accounts and separate money.
- Two shapes, one mechanism (2026-10-21): a pool sponsor adds to the prize pool and is credited on the pool (`sponsor`); a box sponsor adds the same way and also puts their mark on one box (`sponsor_box(box_index, amount)`). The money is identical — the same `Sponsorship` account, the same floor and cap, the same return and commit rules, the same spread across the quarters — and the mark is display only: the box keeps its owner and its prizes, the mark is one sponsor per box (`BoxAlreadySponsored` otherwise), it may sit on an unsold box, and it is never cleared. The pool records which boxes carry a mark (`Pool.sponsored_boxes`, a 25-bit mask) and each sponsorship records its own boxes (`Sponsorship.boxes`), so a client can draw the marks from the accounts alone and the `BoxSponsored` event carries the index for indexers. Which of the two a sponsor is offered, at what amount a pool sponsor becomes the headline sponsor, and what the app shows on a marked box are product decisions on top of this (DESIGN §4.3); the program allows both from the first deployment so neither needs an upgrade later.
- Cost to the keeper: one extra transfer per sponsor on a return, one `close_sponsorship` per sponsor when the pool closes (rent back to the sponsor; permissionless, so a sponsor can also close their own once the pool is terminal). Sponsorship earns the platform nothing directly; it exists to make pools worth more to the people in them.

### Payouts
- The creator picks a payout split at creation from a fixed set of exactly three presets, defined as an enum in the program, not as config: `Standard` = Q1 20% / Q2 20% / Q3 20% / Q4 40% (the default), `Even` = 25/25/25/25, and `FinalOnly` = Q4 100% (winner-take-all on the final score). `create_pool` takes the enum value and rejects anything else; there is no free-form split, so every client shows the same three options and every pool's split is one of three known shapes. The only thing config chooses is which preset the app pre-selects. Adding a preset is a program upgrade. Splits are shown on the pool.
- Fees (platform, creator base, creator add-on, and integrator fee if set) are taken in the same transaction as the first prize with a non-zero share: Q1 for most splits, the final for Q4 100%. Details and amounts under Fees.
- Q1–Q3 use each team's cumulative score at the moment the quarter ends on the game clock (the per-quarter points the line score shows, added up — not the live in-progress score).
- Q4 uses the final score. If the game goes to overtime, the final score after overtime replaces the end-of-Q4 score (the standard rule in the game), so the Q4 prize is paid when the game is final, not when the fourth quarter clock runs out. The keeper must recognise overtime periods and wait for the sources to agree on a final status.
- Push payouts: the settle instruction transfers the prize directly to the winning box owner's wallet. Players never claim.
  - SPL tokens (SKR, ORE): buyers already hold a token account from buying in. Settle and return still use an idempotent create for the recipient's associated token account, because a buyer may close an empty account after spending their tokens; this is a no-op when the account exists and the keeper pays rent when it doesn't.
- Rounding: integer division leaves less than one base unit per share, so at most 3 base units in total on any preset (≤ 24 on the 25-way suspended split), regardless of pool size. This dust goes to the platform and isn't itemised in the pool view; the fee is.
- Rent exemption is never an issue for payouts: the smallest possible quarter prize (0.05 SOL boxes, 15% fee, 20% quarter) is 0.2125 SOL, far above the ~0.0007 SOL a system account needs.
- Every payout, return, and split is recorded on the pool account (quarter, winning box, amount) and emitted as a full event (quarter, score, winning box, wallet, amount), so anyone can verify results on-chain. The app shows this per pool with explorer links to the transfer transactions.

### Randomness
- Entropy, the commit-reveal randomness program Regolith Labs wrote for ORE ([regolith-labs/entropy](https://github.com/regolith-labs/entropy), Apache-2.0; ORE picks its winning square with it), run as MyBarPool's own deployment. The platform deploys a fork of the Entropy source at the commit verified on mainnet (`f26ae03`), published at [war2wigz/entropy](https://github.com/war2wigz/entropy), built and deployed through the same verifiable-build pipeline as this program, with the same Squads multisig as upgrade authority, and verified on-chain against the fork. The fork changes four things and nothing else: the program id, the `Open` instruction, the `security.txt` contact, and `Sample`, which fails instead of recording a predictable fallback when the slot hash it needs is not in the sysvar (see the timing bullet). `Open` is the change that made the fork necessary: Regolith disabled it in their deployed program (the dispatcher arm is commented out at `f26ae03`, since their commit `80d432e` of 2025-11-01; confirmed against the mainnet bytecode on 2026-10-07, a well-formed `Open` fails with `InvalidInstructionData`), so nobody but Regolith can create a `Var` on their deployment, their provider API offers no way to ask for one, and a request to them had not been answered when this was decided. The `Var` layout, `Reveal`, `Next`, `Close` and the keccak formula are Regolith's code, unmodified. The provider — the party that picks the seed, publishes its commit and reveals it — is the platform's keeper. If Regolith re-enables `Open` and offers provider commits, switching back is a constant and a config field (see the decisions log).
- How it works (Regolith's design, unchanged): commit-reveal plus slothash sampling. The provider picks a 32-byte seed and publishes `commit = keccak(seed)` by opening a `Var` account with that commit and an end slot. After the end slot, the hash of that slot is sampled on-chain from the `SlotHashes` sysvar, the provider reveals the seed, the program rejects a seed that doesn't match the commit, and `Reveal` finalizes value = keccak(slothash ‖ seed ‖ samples). The provider can't predict the slothash and nobody else knows the seed, so neither party can steer the result on its own; the platform runs no validator.
- For MyBarPool: at lock the keeper generates a seed, stores it durably (encrypted under a KMS key, written before anything is sent to the chain, so a crash between `Open` and `Reveal` never loses it), opens one `Var` with `commit = keccak(seed)` and an end slot 150 slots later (about 30 seconds at the 200 ms slot time mainnet reaches at epoch 1052, October 2026; a minute at the old 400 ms), and binds it to the pool with `set_var`, which records the `Var` address, its end slot and its commit on the pool account. The digits are unknown to everyone, the platform included, while boxes are on sale and until the end slot has passed. At the end slot, `Sample` runs through this program's own `sample_var` instruction, which anyone may send: it CPIs into Entropy and then reads the `SlotHashes` sysvar itself to check that the hash the `Var` now carries is the real hash of its end slot, recording that hash and the slot on the pool. The keeper then reveals the seed (Entropy's `Reveal` accepts any signer who knows it; only the keeper does), calls `draw`, and closes the `Var` to recover its rent.
- Two independent axis shuffles: the home (top) axis uses `hash(value, "home")` and the away (side) axis uses `hash(value, "away")` as seeds for separate Fisher–Yates shuffles of 0–9. The axes are never a copy of one another. Coincidences (the same pair appearing on a column and a row, even the same lane) are possible and accepted; they don't change any box's odds. The digit assignment is recorded on the pool account and emitted as an event.
- Timing constraint: `Sample` needs the hash of the end slot to be in the `SlotHashes` sysvar, which holds the 512 most recent produced slots (about 100 seconds at 200 ms slots; it was three and a half minutes at 400 ms, and every window in this design is specified in slots, never seconds, for that reason). A bank's sysvar holds the hashes of the slots before it, so the entry appears in the first slot after the end slot, not in the end slot itself; and a slot that was skipped (no block produced; mainnet skips a few percent) never gets an entry. Regolith's `Sample` substitutes a deterministic hash of the slot number in every case the lookup misses — too late, too early, or never — which anyone could compute in advance; the first of those is the "missed window" the design always handled, the second let any wallet poison any pool's `Var` by landing a `Sample` in the end slot itself, and the third is bad luck at the network's skip rate. The platform's deployment instead fails the `Sample` and writes nothing, so a `Var` whose slot is not yet, no longer or never in the sysvar stays unsampled and can be sampled a slot later or replaced. The keeper samples from the slot after the end slot, retries until the window closes, and when the end slot was skipped (no entry for it once the sysvar's newest entry is past it) goes straight to the replacement path without waiting for the window; the base rate of that path is the network's skip rate per pool — of the order of one draw in twenty to fifty needing a `replace_var` from the multisig — and the runbook budgets for it (who signs, how fast; three skips in a row on one pool is of the order of one in ten thousand and ends in `cancel_pool`). A `Var` that is never sampled counts as a failed draw: replacement `Var`, then cancel-and-return if that fails too. The program's own defences against a fallback value stay and are tested with planted `Var`s: `sample_var` only records a hash it has itself matched against the `SlotHashes` sysvar (so a late sample, whoever made it, fails there), and `draw` additionally refuses a hash equal to the fallback formula — neither trusts which deployment wrote the `Var`. `sample_var` itself is permissionless, so the SDK and the verify page expose it: anyone, not only the keeper, can sample a pool's `Var` in the window, and a pool's draw stays honest even if the keeper is down for the 100 seconds that matter.
- What the draw trusts, and what it doesn't. `draw` verifies the whole chain itself rather than taking the `Var` on faith: the `Var` must still carry the slot hash `sample_var` matched against `SlotHashes`; `keccak(seed)` must equal the commit `set_var` recorded on the pool before the end slot; `samples` must still be 1; and `value` must be the keccak of exactly those three. The axes come from that value. So the digits are a function of a commit fixed on the pool before the end slot and the real hash of a slot nobody knew at the time, and nothing the Entropy deployment does can change them: an upgrade of it, or any bug in it, could at most stop a draw, never steer one. The only code that could steer a draw is this program, whose upgrades are public, verifiable and multisig-gated (see Open source and third-party clients).
- Trust assumptions, now that the platform is the provider. The platform holds every seed, so between the end slot and the reveal it knows the value before anyone else does. What it could do with that is refuse to reveal, and the program makes that worthless: a `Var` that has a verified sample cannot be replaced (`replace_var` refuses it), so a sampled pool's only exits are the reveal or `cancel_pool`, a 100% return of every box and sponsorship — aborting a draw whose outcome the operator dislikes costs the operator its fee and gives nobody anything. It cannot choose the seed to fit, because the commit is fixed before the slot hash exists. It cannot rely on a missed window to get a second chance, because anyone can sample in the window, and a replacement `Var` — bound only by the multisig, only when no sample was recorded, capped at two, each one an event on the verify page — is opened with a fresh commit before its own end slot, so it is a new fair draw, not a choice between two outcomes. The 2026-10-23 internal audit closed the two ways the record could have been slipped: the pool is bound to the end slot `set_var` recorded, not only to the `Var` address and commit, so a `Var` the keeper closed and re-opened at the same address with the same commit and a later end slot (Entropy allows it) is refused at `sample_var` and at `draw`, and the keeper may not bind an end slot more than 1,500 slots ahead (the admin's replacement, opened for a multisig that takes hours, is not so bound); and `replace_var` is refused while the recorded end slot is still in `SlotHashes` — a replacement is possible only once the window is actually gone, so there is never a moment when both an honest sample and a replacement are available. What remains, and is disclosed rather than hidden: a replacement is a new draw, so across the original and up to two replacements the platform's keys could, by letting a window lapse unsampled, choose which of at most three independent fair draws a pool gets — never a specific outcome, and only by leaving a public window of about 100 seconds in which anyone can sample. Each replacement is an event on the verify page. Two more residuals the audit named and the program does not address: the commit-reveal removes the keeper-alone and validator-alone cases, not the pair — a keeper who chose an end slot in a colluding leader's turn and shared the seed would let that leader grind block contents toward a value; the leader schedule is public, the keeper's end slot is 150 slots out and visible on the pool, and the platform runs no validator, so this is an accepted residual common to every slot-hash scheme, not a property the program proves. And nothing marks a `Var` as taken: the keeper could bind one `Var` to two pools and give them identical axes — no bias, no misdirected money, and visible on the verify page, so it is a keeper-trust item, not a check. Players therefore rely on the platform for liveness (that the draw happens, and that the keeper reveals), not for fairness (what the digits are). The platform runs no validator; a validator who produced the end slot's block could not use it without the seed. Fallback if the draw isn't finalized within a set time after lock: the admin (multisig) binds a replacement `Var` through the instruction described under no re-rolls, and the keeper retries the draw; the real deadline is the first score post, not kickoff: a pool that fills in the last minute still gets its draw, and `settle` refuses a pool whose digits aren't drawn. If the draw still hasn't finalized when the keeper is ready to post the first score, the admin cancels the pool and the keeper returns every purchase.
- No re-rolls: the pool records the `Var` address and commit at lock and the draw instruction only accepts a value from that account against that commit. Binding a replacement `Var` to a pool is an admin (multisig) instruction that emits an event, is refused once a sample has been verified, and is never a keeper action, so a draw can't be quietly abandoned because someone disliked the outcome. Entropy's `Open` does not require the provider to co-sign (the check is commented out in Regolith's source and the fork leaves it so), and the program does not pretend to prove where a commit came from: `config.entropy_provider` is a label that keeps the verify page honest, and the properties that make a known seed worthless are the ones above: the slot hash is unknown to everyone until after the end slot, the commit is fixed before it, a fallback hash is refused, a sampled `Var` is never replaced, and replacements are capped at two before the only remaining move is a full return. One draw per pool, enforced.
- Cost, from the Entropy source: the program takes no fee and the platform is its own provider, so there is no per-variable charge from anyone. On-chain cost per pool is the `Var` rent (about 0.0026 SOL for the 240-byte account, paid at `Open`, recovered at `Close`) plus five transaction fees, under 0.001 SOL. Deploying the fork costs its program rent once (about 0.7 SOL for a 99 KB program), recoverable if the deployment is ever closed.

### Fees

What is charged:
- Base fee: 10% of the pot on every pool, split 5% to the platform and 5% to the creator automatically. Players see "Fee 10%"; the creator share comes out of it, not on top.
- Add-on budget: up to 5% of the pot on top of the base, chosen at creation, fixed for the life of the pool, and displayed on every pool as part of one total fee. Total rake is therefore 10–15%. The budget is shared between two optional recipients:
  - Creator add-on (`creator_addon_bps`, 0–500): extra fee to the creator, default 0.
  - Integrator fee (`integrator_bps`, 0–500, with `integrator` wallet): a fee to the client that created the pool, for third-party frontends that let their users create pools and need a reason to. The MyBarPool app never sets it. `creator_addon_bps + integrator_bps ≤ 500` is enforced by `create_pool`, so the maximum rake is 15% no matter which client created the pool.
- Why an even split: creators fill the grid, and a pool only locks when they do. At 5% the smallest pool pays a creator 0.0625 SOL, which clears the ~0.010 SOL creation fee several times over, so creating is worth doing even for strangers at the minimum price. The platform's 5% pays for the keeper, the score feeds and the randomness on every pool.
- Why the integrator fee comes out of the add-on budget rather than the platform's 5%: a share of the platform's 5% would be a leak, since anyone with the SDK could tag their own pools and skim, and closing it would need an admin-approved integrator list. Inside the add-on budget, self-tagging gains nothing a creator couldn't already give themselves, so there is nothing to police. Subsidies for large partners, if ever, are off-chain deals.

Amounts (all in the pool's token, integer base units, computed once from the pot `P = 25 × price` and stored on the pool account at creation so they never drift):
- `platform_fee = floor(P × 500 / 10000)`
- `creator_fee = floor(P × (500 + creator_addon_bps) / 10000)` — the 5% and the add-on are one transfer to the creator; `creator_addon_bps` is stored separately on the pool so the event and the UI can break out both components.
- `integrator_fee = floor(P × integrator_bps / 10000)`, zero when unset.
- `prize_pool = P − platform_fee − creator_fee − integrator_fee + sponsored_total`, where `sponsored_total` is whatever sponsors have added by kickoff (see Sponsorship; zero on most pools). Fees are never computed on it.
- `quarter_prize[q] = floor(prize_pool × split[q] / 100)`, computed at the first settlement, when `sponsored_total` can no longer change; whatever integer division leaves over (a few base units) is swept to the platform when the pool closes (to the creator on an abandoned-pool close).

When fees move, and the one rule behind it: **no fee leaves the vault until the pool has paid a prize.**
- Every share (platform 5%, creator 5% plus add-on, integrator fee if set) is transferred in the same `settle` transaction as the first prize with a non-zero share, atomically with it. That is Q1 for 20/20/20/40 and 25/25/25/25, and the final for Q4 100%. There is no separate fee instruction and no fee at lock, at draw, or at creation. The creation fee (account rent) is separate: paid by the creator at creation, reclaimed by the platform at close (see Pool creation for the abandoned-pool exception).
- Until that moment the vault holds the full pot and every sponsorship, so every return path (unfilled at kickoff, postponed, cancelled, draw failure, suspended before the first settlement) is 100% of each purchase and 100% of each sponsorship with nothing to claw back. A creator whose pool is returned earns nothing, which is right: no game, no fee.
- After that moment the fee is final, and so is any sponsorship. A game suspended later splits only the remaining `prize_pool`, not the fee; the platform and creator keep it because the work the fee pays for (draw, keeper, settlement) has been done.
- Destinations: the creator wallet and integrator wallet stored on the pool. SOL goes to the wallet directly; SKR/ORE go to its associated token account with an idempotent create, keeper paying rent if the account is missing, same as winners.
- Every number is fixed at creation and shown on the pool for everyone ("Fee 12% · platform 5% · creator 7%", or with a client line when an integrator is set: "Fee 12% · platform 5% · creator 5% · client 2%"), and to the creator as "You earn 0.0875 SOL with the pool's first prize".

Worked example, 0.05 SOL boxes, 2% add-on, 20/20/20/40: `P` = 1.25 SOL. Total fee 12% = 0.15 SOL (platform 0.0625, creator 0.0875 = 0.0625 base + 0.025 add-on). `prize_pool` = 1.1 SOL, quarters 0.22 / 0.22 / 0.22 / 0.44. The Q1 `settle` transaction moves 0.22 to the Q1 winner, 0.0625 to the platform and 0.0875 to the creator; the vault goes from 1.25 to 0.88 SOL and holds only unpaid prizes from then on.

Same pool with a 1 SOL sponsorship added before kickoff: fees are unchanged (0.0625 platform, 0.0875 creator, still computed on the 1.25 SOL pot), `prize_pool` = 1.1 + 1 = 2.1 SOL, quarters 0.42 / 0.42 / 0.42 / 0.84. The vault holds 2.25 SOL at kickoff; if the game is postponed, 1.25 SOL goes back to the buyers and 1 SOL to the sponsor.

Why not the alternatives:
- At lock: a postponement after lock would need a clawback or a 90% return. Whole returns are worth more than the creator being paid an hour earlier.
- Per quarter (fee taken from each prize as it settles): four times the transfers and rounding, and the creator is paid in four pieces. The only case where it differs is a suspended game, which is rare enough not to design around.

### What the keeper pays for
- Per pool, the keeper signs about ten transactions: Entropy open/sample/reveal/close on the platform's own Entropy deployment, the draw, four settlements and the pool close. Score posts are shared by every pool on a game. Entropy `Var` rent is recovered on close; there is no randomness provider to pay, because the platform is the provider. Occasionally it also pays the rent to create a winner's missing token account.
- All of that is paid by the platform out of its 5% and the creation fee, for every pool on the program, whichever client created it.

## Trust model
MyBarPool is platform-operated. Every state change after a purchase is performed by keys the platform controls, and the program limits what those keys can do (see Trust model).

| Key | Can do | Held in |
|---|---|---|
| Platform admin | Update platform config (fees within the hard-coded ceilings, price ladders, sponsorship caps, default payout preset, creator limits), pause new pools, purchases and sponsorships (a `paused` flag that never blocks a settlement, return or reclaim), set per-wallet limit overrides, mark a game postponed, cancelled or suspended (which makes its pools returnable or splittable), cancel a single pool, replace a pool's Entropy `Var` (only one that missed its sampling window and only once the window is gone from `SlotHashes`; a `Var` with a verified sample is never replaced; at most two per pool) | Squads multisig controlled by the team, same pattern ORE and Entropy use for upgrade authority |
| Score authority (keeper) | Post quarter scores and kickoff-time changes, settle quarters, act as the Entropy provider (generate and keep each pool's seed, open/sample/reveal/close its `Var` on the platform's Entropy deployment, bind it with `set_var`, run `draw` once the `Var` is revealed — the digits are a function of the commit and the slot hash, so `draw` applies a result, it never chooses one), return unfilled pools, execute returns and splits on games the admin has marked postponed, cancelled or suspended (sponsorships return to their sponsors in the same passes) | Cloud KMS, single-purpose; the key never leaves the HSM |
| Program upgrade authority | Deploy new versions of this program and of the platform's Entropy deployment (an upgrade of the latter cannot change a draw's outcome; see Randomness) | Squads multisig |
| Players / creators / sponsors | Buy boxes (count only; positions assigned by the program), create pools within the creator limits, rotate the gate key on their own private pools, add to any pool's prize pool before kickoff | Their own wallets |

Program-enforced checks on the keeper, so a bug or stolen score key can't drain pools in one transaction:
- Quarters must be posted in order, one post per quarter per game record; scores can only increase.
- Quarter timing. A quarter ends on the game clock; that is what decides the end-of-quarter score, and the keeper posts it when the score sources agree the quarter is over (see Score integrity). The program can't see a game clock, only real time, so it enforces the one thing the game clock implies: a quarter's worth of football takes at least 15 minutes to play. The program therefore rejects any score posted sooner than 15 minutes after kickoff (Q1) or after the previous post (Q2, Q3, Q4/final); it never decides when a quarter ends. These floors are never what triggers a post (real quarters take 40–50 minutes with timeouts, injuries, reviews, the two-minute warning and halftime); they only make it impossible for a bug or a stolen key to post a whole game's scores in seconds.
- Returns of unfilled pools are only accepted once the current time has reached the pool's recorded kickoff.
- Marking a game postponed, cancelled or suspended, and cancelling a single pool (only before its first settlement; afterwards only the game-level suspended path applies), require the platform admin key; the keeper can only execute the resulting transfers, and only after that mark exists. Kickoff updates from the keeper are accepted only while the recorded kickoff is still in the future, must set a time in the future, and must stay within 72 hours of the scheduled kickoff in either direction (the exact rules are under Buying; the lower bound is from the 2026-10-23 audit, so a keeper cannot pull kickoff back to the present and lock a pool early); anything later is a postponement, marked by the multisig and returned. The 30-day reclaim clock runs from the scheduled kickoff stored on the game record, never from a keeper update, so pushing kickoff can't delay it.
- A sponsorship can only ever be returned to the wallet recorded on its own `Sponsorship` account; the keeper supplies the accounts, never the destination.
- The pause flag stops money coming in (`create_pool`, `buy`, `sponsor`) and nothing else: every path that moves money out (settle, return, split, reclaim, close) works while paused, so pausing can never trap funds.
- Abandoned-pool reclaim needs no key at all, but only becomes possible 30 days after the original scheduled kickoff on a pool nobody has resolved, and only ever returns a buyer's own share (or a sponsor's own sponsorship). It is the program's guarantee that no buyer's funds can be locked indefinitely, whatever happens off-chain.

### Solana program
- The complete specification (every account and seed, every instruction with its checks and effects, events, errors, state machines, and the exact box-assignment, shuffle and winner algorithms) is [PROGRAM.md](PROGRAM.md). This section is the summary; PROGRAM.md is what gets built and audited.
- Written with Anchor. ORE and Entropy are written with Regolith's Steel framework; this program reads the Entropy `Var` account and builds the `Sample` CPI from its own declaration of the layout and instruction data (see Toolchain, dependency caveat), so none of the fork's Steel code is compiled into it. The Entropy fork itself is built with Regolith's toolchain as they left it, plus `--arch v3`.
- Accounts: platform config (including the platform fee address and per-token sponsorship caps), pool (including `access_type`, `gate_key`, `creator_addon_bps`, the optional `integrator` and `integrator_bps`, `sponsored_total` and `sponsor_count`), per-(pool, wallet) `Sponsorship` (created and rent-paid by the sponsor, closed with its rent back to the sponsor once the pool is terminal), per-game score record (PDA of game key + scheduled kickoff, shared by all pools on that game; created and rent-paid by the platform when the game is first scheduled, kept permanently as history — about 285 records a season, negligible), vault, per-pool Entropy `Var` (temporary), per-creator open-pool counter per game (PDA of wallet + game, incremented on create, decremented when a pool leaves Open, closed with its rent to the platform when it reaches zero and recreated on the next create), optional per-wallet limit override.
- Creator limits are enforced in the program, not just the app: `create_pool` fails when the wallet's open-pool count for that game is at the limit, and both `create_pool` and `buy` fail when they would take the creator above their box cap in their own pool. `sponsor` fails after the recorded kickoff, below one box price, or above the per-token sponsorship cap.
- Token support: native SOL vault; SPL token vaults for SKR and ORE. ORE mint `oreoU2P8bN6jkk3jbaiVxYnG1dCXcYxwhwyK9jSybcp`, 11 decimals (ORE calls base units "grams"), classic SPL Token program (`Tokenkeg…`), no freeze authority — confirmed on mainnet 2026-10-01. SKR mint address, decimals and token program TBD at build time; if SKR is Token-2022, the program's transfer-fee/transfer-hook rejection applies.
- Checked arithmetic everywhere; score authority separate from platform admin.

### Private pools
Gating ships in the v1 program even though the v1 app only creates public pools, so third-party clients can use it from day one without waiting for a program upgrade.
- Anything that restricts who can buy must live in the program. The app can hide a pool from its list, but anyone who reads the chain can find the account and send `buy` directly, so "private" only means something if the program refuses the transaction.
- No passwords on-chain. Accounts and transactions are public, so a code stored on the pool or passed to `buy` is visible the moment it's used. Instead, a gate key: the client generates a throwaway keypair at creation, the public key is stored on the pool as `gate_key`, and the private key goes into the invite link (and a QR code a bar can print). `buy` on a link-gated pool requires the gate key as a co-signer; the client signs silently for anyone who opened the link. The key never appears on-chain, only signatures from it. Same pattern NFT mints use for third-party-signer gating.
- `access_type` on the pool: `public` (default), `link` (gate key required), `allowlist` (Merkle root of allowed wallets on the pool, buyer supplies a proof; for closed groups where a forwardable link isn't enough). Fixed at creation. The tree is PROGRAM §6.4: sha256 with a leaf/node prefix byte, sorted pairs so proofs carry no direction bits, the wallet list sorted and deduplicated so a root is recomputable from the list; the SDK builds roots and proofs, the program only verifies. The creator's own initial boxes at creation are not gated (they set the gate); every later `buy`, the creator's included, is.
- `rotate_gate_key`: creator-only instruction to replace the gate key, killing a leaked link.
- Private pools are otherwise identical: same fees, draw, settlement, returns, and creator limits. The keeper doesn't distinguish them. Listing is a client concern: the MyBarPool app will not show `link` or `allowlist` pools on the game page, only via their link and in My Boxes / Pools I created.
- The gate key is a bearer credential; anyone the link is forwarded to can buy. That is the intended behaviour for a bar. Use `allowlist` when it isn't.
- "Private" therefore means unlisted by the MyBarPool app and gated by whoever holds the key, nothing more. A third-party site can hold the key itself and offer the pool to all of its visitors: public on their site, absent from the MyBarPool app, and it still pays the platform fee and is served by the keeper. That is an intended use, alongside creating ordinary public pools that also appear in the MyBarPool app. Partners who need more than the default open-pool limit get a per-wallet override.

### Open source and third-party clients
- The program (`programs/mybarpool`) is open source under Apache-2.0, the licence ORE uses, and deployed with verifiable builds (see Toolchain). `packages/shared` is published as the client SDK under the same licence. The app, keeper, scores service, and infrastructure stay proprietary.
- Why: the program holds the money, and its bytecode is public regardless. Verifiable builds are only meaningful if the source is public, and a platform-operated real-money game needs that trust argument more than it needs to hide 2,000 lines of Anchor.
- Anyone may build a frontend, bot, or integration. Everything that matters is enforced by the program, not the client: the platform fee is paid to the config account's fee address inside `settle`, the creator fee, add-on and integrator fee are paid the same way, price steps and creator limits are checked on `create_pool` and `buy`, and private-pool gating is checked on `buy`. A client can't turn any of it off. The keeper watches every pool account on the program and serves third-party pools identically; the 5% and the creation fee cover that cost.
- What a third party chooses and what it doesn't: everything that is a per-pool choice is the client's (token, price, payout split, creator add-on, integrator fee, public or private, which of the allowed tokens its UI offers at all, whether to expose sponsoring); everything that is a list or a ceiling is the platform's (allowed tokens and their mints, price steps, fee caps, sponsorship caps, creator limits). Sponsorship is program-level, so a pool sponsored through one client shows as sponsored in every client that reads the chain. A client that wants only ORE pools offers only ORE; a client that wants a token not on the list asks, and if added it is added for everyone by config.
- How a third party earns: either as the sole creator on its own site (5% base plus up to 5% add-on on every pool, with a per-wallet override for the open-pool limit), or by letting its users create pools and setting itself as `integrator` for a share of the add-on budget. What it cannot change: the 5% to the platform and the 5% to the creator. Different terms mean a fork, and a fork means running a keeper.
- The fork case: someone can deploy their own copy with their own fee address. They then need their own keeper, score feeds, Entropy integration and mainnet operations; the MyBarPool keeper serves only the official program ID.
- Nothing privileged is hidden. Every admin capability is an explicit, documented instruction gated on the multisig (see Trust model). A quiet exception in `buy` or `settle` would be found by anyone reading the source or the bytecode, and would end the product.
- Guarantees to integrators, enforced in code rather than promised: the platform fee and the 15% total cap are hard-coded ceilings in the program (`platform_bps ≤ 500`, `base + add-on budget ≤ 1500`); config can lower them, never raise them, so raising fees would need a program upgrade, which is public, verifiable, and announced. Every pool's fees are fixed on its account at creation, so no change of any kind touches an existing pool.
- Upgrade discipline, since third-party clients depend on layouts and events: the pool and config accounts carry reserved padding so fields can be added without migrations; the IDL is published on-chain and versioned; events are additive only; breaking changes get a deprecation notice in the public changelog at least one NFL week before deploy. Official program ID and config PDA are published in the public repo so clients can check they're talking to the real deployment and not a fork.
- Trademark: Apache-2.0 covers the code, not the name or the sign. The public repo carries a notice that "MyBarPool", the helmet mark and mybarpool.com are trademarks of the team and may not be used by forks or clients to imply endorsement. Clients say "powered by MyBarPool" or nothing.
- Security: [`SECURITY.md`](../SECURITY.md) with a disclosure route and a response commitment; an internal security audit of the program before the first mainnet deploy, with the report published under [`docs/audits/`](audits/) (the 2026-10-23 report is the first; the decisions log has why an external firm was not engaged); a bug bounty once there is enough in vaults to justify one, published in the SEAL Safe Harbor form (OtterSec maintains the Solana registry program for it) so a whitehat who moves funds to safety during a live exploit has terms to point to rather than a promise in a README. Dependency licences (Anchor, `entropy-api`, Steel) are checked for Apache-2.0 compatibility before the program is published.
- Contributions: issues and discussion welcome; the program does not accept external pull requests in v1. It holds money, and review capacity is the constraint. Revisit after the first season on mainnet. See [`CONTRIBUTING.md`](../CONTRIBUTING.md).

It is a development build (`expo run:android`); Expo Go cannot load the wallet adapter's native modules.
- One Kit major per lockfile, and the app's is the SDK's. As of 2026-10-01 that is not yet automatic: the SDK (Codama's renderer), the keeper (keychain 2.0), the web wallet stack and Solana Mobile's own web template are all on Kit 8, but Solana Mobile's `expo-kit-wallet` template and `@wallet-ui/react-native-kit` 4.3 still depend on Kit 7, because the Mobile Wallet Adapter Kit package they wrap (`mobile-wallet-adapter-protocol-kit`) only reached Kit 8 in a 3.0.0 canary published that evening; wallet-ui's move to Kit 8 is an open PR waiting on that release. The rule for the builder: never carry two Kit majors in the app, and never force Kit 8 under wallet-ui 4.x with lockfile overrides. Scaffold the app in Step 0 regardless (12a and 12b touch no chain code); before 12c, take wallet-ui's Kit 8 release if it has shipped; if it has not, drop wallet-ui and use `@solana-mobile/mobile-wallet-adapter-protocol-kit` 3.x directly behind the same thin provider and hook — it is the layer wallet-ui wraps, and the `solana-mobile-wallet` skill documents both. Either way the app's lockfile ends up on the SDK's Kit 8 before any chain code is written.
  - Android (Seeker, dApp Store) — native APK, signing via Mobile Wallet Adapter (Seed Vault and installed wallets), push notifications via FCM, haptics, share sheet, .skr names on the grid.
  - Web (mybarpool.com) — the same screens rendered with React Native Web, signing via wallet-standard (Phantom, Solflare, Backpack, and Seeker Connect, below).
- Web wallet stack, taken from Solana Mobile's own web template (`react-kit-shadcn`) and the Solana Foundation's `solana-dev` skill so we are on the path both vendors maintain: Kit's wallet plugin (`@solana/kit-plugin-wallet`) with `@solana/react` and `@wallet-standard/react` for discovery and connection, plus two wallets registered at startup: Seeker Connect and `@solana-mobile/wallet-standard-mobile` (Mobile Wallet Adapter exposed as a wallet-standard wallet, for Android browsers generally). ConnectorKit (`@solana/connector`) and framework-kit were looked at and not used: they solve the same problem one layer up, and one wallet stack per target is the rule. (On 2026-10-01 the Foundation marked framework-kit unmaintained and pointed new projects at Kit and Anza's kit-plugins, which is where this design already is.)
- Seeker Connect on the web: Solana Mobile's `@solana-mobile/seeker-connect-wallet-standard` is registered as one more wallet-standard wallet, so a Seeker owner who opens a shared link in a browser — on the phone, or on a desktop through Solana Mobile's relay — connects to the Seeker's own wallet directly, with no wallet picker and nothing to install. It is built on Mobile Wallet Adapter, not a second protocol, and it is what makes "the link works everywhere" true for the users the app is aimed at.
- A small wallet abstraction sits between the screens and the two signing paths (MWA on Android, wallet-standard on web) so screens never know which one they're on.
- `@solana/kit` is the one Solana client library across the app, the SDK in `packages/shared` and the keeper. The SDK's account decoders and instruction builders are generated from the Anchor IDL (Codama), so the app and third-party clients consume the same generated client and nothing is hand-decoded twice.
- `.skr` names (AllDomains names on mainnet, one per Seeker by default) are resolved by the scores service, not by phones: one cached reverse lookup per address, served to the app in batches, so a grid of 25 owners is one request and no RPC key ships in the APK. Names are labels only; the app never resolves a name forward to send money anywhere.
- Precedent: ORE's app ships web, mobile and Seeker from one codebase (Dioxus, Rust). MyBarPool takes the same approach in TypeScript so the app shares `packages/shared` with the keeper and program tests.
- If the dApp Store rejects a real-money game, MyBarPool ships as the web app only; nothing in the design depends on the store.

### Sharing and links
Selling a grid is mostly a creator sending a link, so links are part of the architecture, not a frontend detail. The design (text, sheet, QR, printable board) is in DESIGN.md, Sharing; this is what has to exist underneath it.
- Canonical pool URL: `https://mybarpool.com/pools/{poolAddress}`, the pool PDA in base58. The web app reads the pool directly from the chain, so a canonical link works with nothing but an RPC and is what the SDK and third-party clients should link to. Nothing on-chain changes for sharing.
- Short link: `https://mybarpool.com/p/{code}`, `code` = first 8 base58 characters of the pool address (58⁸ ≈ 1.3 × 10¹⁴, so a prefix collision within one program's pools is not a practical concern; the resolver returns "not found" rather than guessing if it ever sees two). Resolved by prefix lookup in the scores service's pool index and answered with a redirect to the canonical URL. It is a convenience layered on the canonical link, never a dependency: if the resolver is down, every canonical link still works.
- Link previews: pool and game pages are served with Open Graph and Twitter card metadata and a per-pool preview image of the current grid, rendered server-side, cached, and invalidated on every buy, lock, draw and settlement event the scores service already observes. The renderer is the same grid component the app uses, run in a headless renderer on the server, so previews, shared images and printed boards are identical.
- Android App Links: `https://mybarpool.com/.well-known/assetlinks.json` lists the Seeker app's signing certificate so verified links open the app directly; the same URL opens the web app when the app isn't installed. No custom URL scheme is exposed to users.
- Private pools: the gate key travels in the URL fragment (`#k=…`), which browsers never send to the server, so it stays out of request logs, the redirect and the preview renderer. The preview for a private pool omits the grid and names.
- No tracking parameters on shared links and no referral mechanics; the pool address is the only identifier a link carries.

### Identity, profiles and pool chat
A board in a bar has names on it and people talking around it; the app has addresses and silence. This section adds the two without adding accounts: the wallet is the identity, a profile is a label a wallet puts on itself, and chat is the conversation of the people who hold boxes in one pool. Nothing here touches money or the program, which stays as audited; every piece is optional, and a wallet that never sets a name or sends a message sees the app exactly as today. Precedent: ORE's app — optional profiles with a chosen name and picture, and one wallet signature the first time you chat, after which messages flow without the wallet.
- Identity: the wallet address, nothing else. No e-mail, no password, no account table, no linking of wallets. The service never knows a person; it knows a public key that signed something.
- Profile: a `username` (3–20 characters, letters, digits, spaces, `_`, `.`; not unique, since the address is the identity and the name is a label) and an avatar, both optional, set from the wallet chip. Shown wherever the app shows a short address today — the grid, the boxes list, activity, payouts, chat — with `.skr` names offered as a default when a wallet has one and the short address as the fallback for everyone else. Reserved names: the directory sponsors' names, team names, "MyBarPool" and its variants are refused, and a directory sponsor's mark comes from the directory alone, never from a profile, so a profile cannot impersonate a sponsor or the house.
- Avatar: uploaded through the service, 1 MB cap, decoded and re-encoded server-side to a fixed 256 × 256 WebP (nothing a browser hands us is served back as it came: no SVG, no metadata, no oversized file), stored under a content hash, served through the same CDN as `/v1/avatars/{hash}.webp`, immutable, so changing an avatar changes the URL and nothing is invalidated. Avatars appear in the app; they never appear in the saved image, the printed board or the link preview, which carry names only, so an image we rendered never carries one we did not review.
- Where the profile lives: in the scores service's store (one table, wallet → profile), written only by the wallet that owns it. An on-chain profile account (readable by ORE's app and others) was considered and deferred: the program is frozen at launch and a separate program is a second audit; the decision is in the log and the table's shape is chosen so an on-chain copy can mirror it later.
- Writes are signed, never logged in. Setting a profile is one `signMessage` by the wallet over a short statement (domain, action, nonce, time), verified by the service, which proves the wallet without a session, a cookie or a token store. The first chat message is the one-time wallet signature the design calls for: it authorizes a device key — a keypair the app generates and keeps on the device — with a statement the wallet signs once ("Let MyBarPool post messages as you from this device"); every message after that is signed by the device key and carries the wallet's authorization with it, so anyone, the service included, can verify who wrote it and the wallet is never asked again. A new phone or a cleared browser means one signature again. Authorizations expire after 90 days and a wallet can revoke every device from its profile.
- Pool chat: one thread per pool, no direct messages. The thread is also the pool's activity: the program's events (purchases, sponsorships, lock, draw, each settlement, fees, returns) appear in it as system lines, public to anyone and each opening the pool's own on-chain record page (`/pools/{id}/verify`, which is where explorer links live; no other screen links to an explorer), so a thread is never empty and the audit trail is the same one everyone sees. You can read and post in a pool's thread if you hold a box in it or created it; a sponsor reads. The membership check is the chain state the app already has, and it is the spam filter: nobody can reach you who did not put money in the same pool. Messages are text, 140 characters, no image attachments (the sender's avatar shows beside each one), no links rendered as previews; the one allowance is a curated GIF set bundled with the app and sent by id, never an upload; the service rate-limits per wallet. Transport is the live WebSocket (`chat` messages beside `game`, `pool`, `event`, `leading`); storage is one table keyed by pool with a 30-day lifetime after settlement or return, so threads die with the game and the service is not an archive. Plaintext on the service, stated in the terms: end-to-end encryption between wallets is a later layer on the same thread store, not a change to it.
- Moderation, light first: the creator pins one message and can mute a holder in their own pool, which hides that wallet's messages there and nothing else; most of it ends there. Then, because the stores require it and the bar does too: report on every message and avatar; hide the reported item for the reporter at once; the team removes a message, an avatar or a name from the admin tool, and a wallet removed twice loses chat and profile for the season. Removals are logged with who and why. A wallet never loses its boxes or its payouts for anything it says.
- Notifications: the Seeker app gets a push for new messages on a pool you hold a box in, batched ("3 new messages on your Eagles–Cowboys pool"), off by default per pool once the pool settles; the web gets nothing until the tab is open.
- Private pools keep their rule: the preview and the share image omit names; the thread is only visible to holders anyway.

### Live scores vs. results
The frontend receives two separate streams and must never confuse them:
- Live scores (from the scores service over WebSocket): display only. The grid may highlight the box that would currently win as "leading", clearly marked provisional, and it changes with every score update.
- Results (from on-chain settlement events emitted by the program): the only source of truth for winners and payouts. A box is shown as "won" only after the settle transaction confirms, with a link to it.
Winner calculation happens in the program at settlement, driven by the keeper. Neither the scores service nor the frontend ever decides a winner.

### Score integrity
- Scores are public, so there is no on-chain dispute process. The risk is the keeper posting a wrong score (bad feed data, bug, or a compromised key), and payouts are irreversible.
- Sources, five live and one after the fact, each with a different upstream so a bad feed has to be wrong in the same way three times over. The tiers below (primary, standby) are how the first three were ranked; since 2026-10-14 the live voices are equal under the agreement rule in the decisions log (three of the configured voices must propose the same value), with TxODDS added as a voice on 2026-10-14 and Yahoo on 2026-10-23. None needs a key, an account or a contract:
  - Primary 1, Polymarket's public sports WebSocket (`wss://sports-api.polymarket.com/ws`): unauthenticated, no subscription message, streams every live game with `score`, `period` (`Q1`–`Q4`, `HT`, `OT`, `FT`), `status`, `ended` and a `sportradarGameId`. Upstream: Sportradar, under Polymarket's published data partnership. Polymarket labels it informational and best-effort, so it is treated as a source, never as the source. The end-of-quarter score is the last `score` seen before `period` advances.
  - Primary 2, Kalshi's public live-data API (documented, unauthenticated): per game the points, quarter, clock and status, with Stats Perform named as the provider — a different data operation from Sportradar's. Its game list is also a schedule that carries the Sportradar game id, so the two primaries are matched to one game before kickoff. Kalshi publishes it for its own traders and promises nothing to anyone else, so it is treated the same way as Polymarket's: a source, never the source.
  - Standby, ESPN's public scoreboard feed. Upstream: ESPN's own stats operation. Standby because it is the one source with no agreement behind it, so it is the one most likely to break in a way that looks like a disagreement.
  - TxODDS's free real-time NFL feed (`TxLINE`), with explicit quarter-break and final phases. Upstream: TxODDS's own trading-data operation.
  - Yahoo Sports' public scoreboard feed. Upstream: Yahoo's own sports-data operation. The fifth voice, added so a final — the one decision where the prediction markets' closing frames arrive minutes after the whistle — has three fast voices instead of two.
  - After the fact, nflverse's open data (`games.csv` and the season's play-by-play, CC-BY-4.0, updated nightly in season). Upstream: the league's GSIS feed. Every posted quarter and final is compared with it the next day and a mismatch alerts a person; it is hours late by design, which is what makes it independent of the live feeds, and it never decides anything.
- Agreement rule, the one the keeper applies to end-of-quarter scores, final status, kickoff changes and postponed/cancelled/suspended status alike (since 2026-10-14; the two-primaries-plus-standby rule it replaced is in the decisions log): **post when at least three of the configured voices propose the same value, and have kept proposing it for 60 seconds.** A voice that is unreachable, or has gone stale on a live game, is silent for that decision and alerted on; it is never treated as disagreeing. Fewer than three voices agreeing is a wait, not a halt: nothing is posted, the decision is re-evaluated on every input, an open decision alerts after ten minutes, and whatever is still open after the game is closed from nflverse's official score the next morning (or earlier by an operator settling on a named voice's value, with the choice recorded on the post). No single voice ever decides anything, and a disagreement is never resolved automatically by picking a side.
- Polling: one request per source returns every live NFL game, and the scores service fans that out to all pools over WebSockets, so API usage doesn't grow with the number of pools; the Polymarket stream is push. Only the scores service talks to the sources; clients never do. The live score the app displays is the agreed state from the primaries (Polymarket's push arrives within seconds of a play, Kalshi confirms within its polling cycle); ESPN is never what a user sees unless it is standing in for a primary.
- Mitigations: the agreement rule above; program-enforced ordering and timing checks (see trust model); score authority key is single-purpose and held in KMS.
- Considered and not used as live sources: API-Sports (the paid feed the first draft used as primary 1; replaced by Kalshi's live data on 2026-10-10 and held in reserve as the known replacement should a primary ever be withdrawn — a paid plan and an adapter, no engine change), Sportradar directly (self-serve is a 30-day sandbox trial; production is an enterprise contract, revisit when volume pays for it), sportsbooks (no public APIs), odds aggregators (resellers), and Kalshi's *markets* (binary settlements, hours late — a different thing from its live-data feed). Other free scoreboards (CBS, NFL.com) are unofficial endpoints of ESPN's kind and add parser risk for a sixth voice the rule does not need; Yahoo's, of the same kind, became the fifth voice on 2026-10-23.

## Decisions log
- Three score sources, two primary and one standby (2026-09-27, tiered 2026-09-29; superseded 2026-10-10, see "Four score sources" below): added Polymarket's public sports stream (Sportradar data) beside API-Sports; those two are the primaries and must agree. ESPN is standby: it stands in when a primary is silent, is read continuously, and a disagreement from it alerts a person without stopping the post. Reasons: three different upstreams make a correlated wrong score far less likely than two; one feed being down no longer stops every settlement on a Sunday; and ESPN's unofficial endpoint is the source most likely to break in a way that only looks like a disagreement, so it should not be able to halt games on its own. The two sources actually relied on for a post always have to agree; a disagreement between them is never resolved by the third automatically. Kalshi was checked and rejected as a score source (settlements only, hours late, binary); Sportradar direct is enterprise-only and deferred.
- Entropy (superseded 2026-10-07, see "Entropy, own deployment" below): build against Regolith's deployed program and provider (`entropy-api.onrender.com`, the endpoint ORE's CLI uses). It's open source; talk to Regolith only if something requires it.
- Seeker: submit to the dApp Store; if rejected, web app only.
- Profiles and pool chat (2026-10-17): optional username and avatar per wallet, and one chat thread per pool for its box holders, in v1 (Step 12e, decided 2026-10-18 after first being filed for after launch; the Identity, profiles and pool chat section). Shaped on ORE's app: nothing mandatory, a chosen name instead of an address, and one wallet signature the first time you send a message, authorizing a device key, after which chat is free of the wallet. Rejected: open wallet-to-wallet direct messages (spam and scam inboxes from day one; threads gated to a shared pool are the filter), on-chain messages (a wallet sheet and a fee per message, and nothing can ever be removed), `.skr` as the display name (almost no wallet has one; it is offered as a default and nothing more), and an on-chain profile account for now (the program is frozen at launch and a second program is a second audit; deferred, not refused, and the table is shaped so a chain copy can mirror it). Dialect's messaging SDK was looked at and not used: still a beta in 2026, with the company sunsetting adjacent products.
- NFL logos (superseded 2026-10-08, see "Team marks, no logos" below): use real team logos throughout the app.
- Fee split: 10% base as 5% platform / 5% creator, add-on budget up to 5%, 15% cap, and the creation fee (rent, ~0.010 SOL) kept by the platform. Replaces an earlier 6/2 split with an 8% base: at 2% the smallest pool paid a creator about 0.025 SOL against a ~0.010 SOL creation fee, too thin to motivate creating for strangers; 5% pays 0.0625 SOL. Refundable rent was considered and rejected as an extra path for little gain once the creator share was raised.
- Postponed games are returned, exactly like cancelled ones, even after lock and draw. Decided and confirmed; do not "improve" this into carrying the pool to the new date. Reasons: nobody's money sits in a vault for an unknown number of days, the game record and every pool stay simple, and a creator can open a new pool on the rescheduled game in a minute. Only ordinary league schedule changes announced before the game (flex, moved slot) move a pool's kickoff.
- Fee timing: platform 5%, creator 5%, add-on and integrator fee all move in the first settlement transaction that pays a prize, never at creation, lock, or draw. Amounts are fixed on the pool account at creation. Rejected: fees at lock (breaks whole returns on postponement) and per-quarter fees (4× transfers for a difference that only shows in a suspended game). Confirmed: on a game suspended after the first settlement, the fee stays taken and only the unpaid prize pool is split; a pro-rata fee refund was considered and rejected as not worth the complexity for a once-a-decade case.
- Open source: program and SDK under Apache-2.0 with verifiable builds; app, keeper, scores service and infra proprietary. Third-party clients welcome; fees, limits and gating are program-enforced so they apply to every client. Forks are accepted as the cost of the trust argument.
- Abandoned-pool reclaim: permissionless per-buyer reclaim of their own share on any pool still unresolved 30 days after the original scheduled kickoff. The one exception to platform-only control of returns, accepted because a running keeper never lets a pool reach it, and it is the guarantee integrators and auditors require of any program that holds user funds. Not an outage measure; outages are hours, not months.
- Integrator fee: optional per-pool `integrator` wallet and `integrator_bps`, sharing the 5% add-on budget with the creator add-on so the 15% maximum holds for every client. Gives third-party frontends a reason to let their users create pools. Rejected: paying integrators from the platform's 5%, which would need an approved-integrator list to stop self-tagging.
- Sponsorship (2026-09-29): any wallet can add to a pool's prize pool before kickoff through a `sponsor` instruction; no fee is taken on it, it is spread across the quarters by the pool's preset, and it is returned to the sponsor on every pre-settlement return path and committed once the first prize is paid, exactly like fees. Names, logos and links (website, Seeker app) come from a reviewed directory in `packages/shared`, never from on-chain text; the listing is the sponsor's benefit and the platform's to grant, and any commercial relationship with a sponsor lives there, off-chain, never as a cut of the prize. Chosen over the alternatives considered for making losses smaller: a platform token (a whole second project, and the platform paying players), paying losing boxes from the platform's fee (a promotion, and about 6% of a box back), and yield on the vault (a week of staking on a small vault pays nothing). Sponsorship adds outside money to the prizes without the platform being the one adding it; it is meant for companies and communities that want their name on a game (an ORE sponsor on the ORE pools, say), not for ordinary creators, so it is not a step in the create flow and the creator's 5% is not traded against it. The platform never sponsors, including pools it creates itself. Rejected in the same discussion: letting creators trade their 5% for a contribution (no incentive to use it, and it would make the fee vary per pool), and a cheaper rung on the price ladder (not needed for this; revisit separately if small pools want it).

- Allowlist tree (2026-10-08): sha256 Merkle tree with a 0x00 leaf prefix and a 0x01 node prefix, children hashed in bytewise order, the wallet list sorted and deduplicated first (PROGRAM §6.4). Reasons: sorted pairs keep the proof to the sibling hashes alone, so a client needs no index bookkeeping; the prefix bytes close the second-preimage trick where an interior node is passed off as a wallet; a canonical list order means two clients given the same list compute the same root and anyone can check a root against a published list. - Internal security audit (2026-10-23): an external firm was considered for the program and not engaged. The reasons: the program is 27 instructions and under 7,000 lines of Rust that a focused review covers in full; every rule it enforces is written down in PROGRAM.md, so a review has a spec to check against rather than a design to reverse; and the test harness already proves the mechanics (around 370 Mollusk tests on the SBF binary, a 6.2-million-case fuzz run, the schema snapshot, the anchor-lints pass) — what an auditor adds is adversarial reading, which was done here by four independent reviewers given the code, the spec and no prior context, one slice each (money and arithmetic; draw, randomness and time; accounts and access; gating, configuration, state machines and denial of service), reporting in the fixed audit format every step of the build has used. The report is [`docs/audits/2026-10-23-internal-audit.md`](audits/2026-10-23-internal-audit.md). The draw slice found a Blocker and two Highs that the earlier reviews had missed and the test suite could not have caught, because they were in what the program did not check rather than in what it did: the pool recorded the `Var`'s end slot but never compared it, so the keeper — the `Var`'s authority — could close and re-open it at the same address with the same commit and a later end slot after seeing the first slot's hash, an unbounded re-roll with no event; `replace_var` had no missed-window condition, so a replacement could race an honest sample; and `draw` was allowed after scores were posted, which turned either re-roll into a choice of winner against known scores. All three are fixed and tested (PROGRAM §4.4), with a lead bound on the end slot so a far-future `Var` cannot park a pool beyond the admin's reach, and the residual — up to three independent fair draws by letting public windows lapse, never a chosen outcome — is disclosed under Randomness rather than argued away. The other slices found one High (a Token-2022 destination that requires memos could block `settle`; the program now writes the Memo itself) and the Mediums and Lows the report lists, every one fixed or written down with the reason. What this is not: a third-party attestation. SECURITY.md says so, and says that the report, the tests and the verifiable build are what a reader checks instead. A paid review stays an option once vaults hold enough to justify one, alongside the bounty.

Revisit if support shows "I have SKR and can't buy" as a real pattern.
- Private pools: gate-key (`link`) and Merkle `allowlist` gating built into the v1 program; the v1 app creates public pools only and exposes private pools later. Participants are not capped per pool; a big buyer doesn't change the creator's fee or anyone's odds, and the bar use case is served by private pools rather than a platform rule.
- Creator limits: 3 open pools per wallet per game and 5 boxes in your own pool, both adjustable in config globally or per wallet. Players are unlimited. Chosen to prevent clutter and grid-stuffing, not because self-buying is exploitable (it isn't; see Limits).



## Toolchain
- Always build with the latest stable release of each Solana tool. Stable means a tagged release Anza marks suitable for mainnet; never alpha, beta, or rc builds, which exist for validator operators testing upcoming changes. On 2026-09-25 that is Agave/Solana CLI 4.3.0 (4.4 is alpha only), Anchor 1.2.0, and platform-tools v1.57 behind `cargo build-sbf`; re-checked 2026-09-30 (4.4 reached beta, still not stable) and 2026-10-01 (4.4.0-beta.0 is the newest tag; 4.3.0 remains stable, and it is the release OtterSec and Neodyme audited in September 2026, reports in `anza-xyz/security-audits`); re-checked 2026-10-06: Anchor 1.2.1 is out with one change (a `solana-v4` feature for programs on the 4.x Solana crates) and nothing we need, so 1.2.0 stays pinned until a release carries a fix we want, such as the `has_one` field-name hygiene rule; re-checked 2026-10-07: that hygiene fix (`#5105`) is merged on Anchor's main branch but unreleased, so the identifier rule stays until the release that carries it; Agave 4.5.0-alpha.1 exists and 4.4 is still beta, so 4.3.0 remains the stable release; Surfpool 1.6.0, Mollusk 0.16.0, Kit 8.4.0, Codama 1.11 and `solana-verify` 0.5.2 are unchanged; re-checked 2026-10-20: Agave 4.3.2 is the stable patch (4.4.0-beta.1 and 4.5.0-alpha.2 are not), Surfpool 1.6.1 and Mollusk 0.16.2 are out, all three adopted (the entry under Decisions), Anchor 1.2.0 stays. On the TypeScript side `@solana/kit` 8 (8.4.0), which builds transaction v1 (SIMD-0385, active on mainnet) by default; nothing in the program needs the larger size, but the SDK and keeper get it for free.
- Pin every version in the repo so all builds are reproducible: `rust-toolchain.toml`, the `[toolchain]` section of `Anchor.toml`, and the Node version and package lockfile for the apps and services. CI builds with exactly those pins.
- Upgrade policy: when a new stable ships, bump the pins in a dedicated PR, run the full program test suite on localnet, then merge. Don't let versions drift silently.
- Verifiable builds: deploy with `solana-verify` and submit the build for on-chain verification, as ORE and Entropy do, so anyone can confirm the deployed program matches the public program source (see Open source and third-party clients). CI uses the Solana Foundation's reusable workflow (`solana-foundation/github-workflows` `reusable-build.yaml`, which composes their `github-actions` collection: build, verify, IDL buffer and upload, `use-squads` for the multisig) rather than hand-written workflows, so the verifiable build, the on-chain IDL and the multisig-gated upgrade follow the same steps every other verified program uses. The IDL and the program's `security.txt` (the contact from SECURITY.md) are published on-chain through the Program Metadata Program, where explorers and `@solana/idl` read them; the IDL is not only a file in the repo. How verification reaches OtterSec's registry changed in 2026: `solana-verify`'s `--remote` flag is deprecated; the verify PDA is written by the program's upgrade authority (for us, a Squads transaction the workflow exports) and OtterSec's worker picks new PDAs up from chain, with `solana-verify remote submit-job --program-id … --uploader <vault>` as the manual nudge if `verify.osec.io/status/<program>` has not flipped. The runbook in Step 14 follows that sequence.
- Static analysis: OtterSec's `anchor-lints` (dylint lints for Anchor programs — missing signer and owner checks, duplicate mutable accounts, arbitrary CPI targets, reading an account after a CPI without `reload()`, `SystemAccount` on a seed wallet that could later change owner, and the rest) run in CI on every program change, pinned to a commit, and must be clean; the rules they encode that matter to this program are written into PROGRAM §10 so they hold even where a lint has a blind spot. Considered and not used: OtterSec's formal-verification fork of Anchor (`otter-sec/solana-verify`, nightly-only and experimental); the invariants in PROGRAM §10 are proven by tests instead.
- Solana Mobile tooling: the `solana-mobile` CLI (`create`, `doctor`, `emulator`, `device`) scaffolds the app and checks the Android toolchain; Solana Mobile's `dapp-store` CLI publishes releases to the dApp Store. Solana Mobile's agent skills (`solana-mobile-skills`: project setup, wallet, `.skr` names, Seeker Connect, publishing) and the Solana Foundation's `solana-dev` skill (Anchor, Codama, testing) are installed under `.agents/skills/` in the private repo so the builder model works from the vendors' current instructions rather than from memory.
- Dependency caveat, now a decision: Entropy's `entropy-api` crate (latest 0.1.6, May 2026; ORE pins 0.1.4) is built on Steel and `solana-program ^2.1`, while Anchor 1.2 sits on the 3.x Solana crates. Two `solana-program` majors in one program crate is a type-conversion and link-time mess, so the program does not depend on `entropy-api`: it defines the `Var` layout (PROGRAM §4.4) and the `Sample` instruction data in its own module, with a test that decodes a `Var` fetched from mainnet to prove the layout. The account is small and the layout is public.
- Pins verified 2026-10-01 against the registries, so Step 0 starts from a set that is known to resolve together: Agave 4.3.0; Anchor 1.2.0 (2026-09-04 — the `v0.3x.2` tags dated 2026-09-14 are backports, not newer); platform-tools v1.57; `@solana/kit` 8.4.0 with `@solana/react` 8.4.0; kit-plugins 0.19.0 (`kit-plugin-wallet` 0.20.0; both peer on Kit ^8.2); Codama 1.11 with `@codama/renderers-js` 2.5 (generates against Kit ^8.3); `@solana/keychain-*` 2.0.0 (peer Kit ≥8.1); Mollusk 0.16.0 (2026-10-05; built on the Agave 4.3.0 crate set, so the `solana-program-runtime = "=4.2.0"` dev-dependency pin that 0.15.1 needed is gone — Step 3 made the bump; it checks rent exemption on every account by default, which our fixtures satisfy); host rustc 1.97.1 in `rust-toolchain.toml` for Mollusk and the IDL build, while the crate's `rust-version` stays 1.89 for the SBF side (platform-tools v1.57 ships rustc 1.95); Surfpool 1.6.0; `litesvm` 0.17 under `kit-plugin-litesvm` 0.19; `solana-security-txt` 1.1.3; `solana-verify` 0.5.2; Node 22 LTS (`@wallet-standard/react` 1.0.3 requires ≥22; 22 is in maintenance until 2027-04, so moving to 24 is a Step 0 judgment call, not a blocker). Added in Step 1 (2026-10-04): `@noble/hashes` 2.4.0 as the SDK's one runtime dependency, a synchronous, audited SHA-256 so the reference algorithms of PROGRAM §6 run in React Native, where WebCrypto is absent (Node's `node:crypto` would tie the SDK to Node); and `@vitest/coverage-v8` 5.0.3 as a dev dependency for the SDK's branch-coverage gate. Two things that do not line up and are handled explicitly: `@solana/idl` 0.2.0 still peers on Kit ^6.4, so it is run with `npx` in the Step 14 check and is never a dependency of the SDK; and the Android wallet layer is on Kit 7 today (see Clients). One more: OtterSec's `anchor-lints` pins `nightly-2025-09-18` and tests against an Anchor fork, so Step 0 confirms it compiles against Anchor 1.2 code before making it a required job; if it does not, the three rules in PROGRAM §10 are checked by the auditor by hand and the job waits for a lint release that does.
- Bytecode version: SBPFv3 from the first build. Mainnet has executed SBPFv3 since June 2026, and SIMD-0500 (feature `B8JJXCy5amZyWG9r7EnUYLwzXSXTxG7GZ1qZ1qggo83g`, planned for Agave 4.4, expected on mainnet in November 2026) will make the loader reject any deployment, upgrade or authority freeze of a program whose ELF is v0, v1 or v2 — right around launch. The catch is that the pinned tools still default to v0: `cargo build-sbf` 4.3.0, `anchor build` and `solana-verify` 0.5.2 all take `--arch v3` but do not assume it (the 4.4 CLI flips the default). So every build command in the repo passes `--arch v3` explicitly — `anchor build --arch v3` (the flag Anchor 1.2.0 added), `solana-verify build --arch v3`, `solana-verify remote submit-job --arch v3` — and CI fails the build if `readelf -h target/deploy/mybarpool.so` does not report `Flags: 0x3`. The Foundation's `build-verified` action has no arch input yet, so the Step 0 workflow runs `solana-verify build --arch v3` in its own step until it does. Toolchain minimums for v3 (platform-tools ≥1.53, cargo-build-sbf ≥4.0, Anchor ≥1.2.0) are all met by the pins; v3 refuses undefined symbols at link time, which Anchor 1.2 handles. Mollusk, LiteSVM and Surfpool execute v3, so tests cover the same bytecode we deploy.
- Mainnet's validator version doesn't gate program builds. Programs compile to SBF bytecode that runs on any supported cluster version; only new syscalls or SBF features need the matching feature gate active on mainnet.

## Environments
- Two environments only: localnet and mainnet. No devnet.
- Tested devices: Seeker (primary), the Android emulator with Solana Mobile's Fake Wallet (development and CI), and an ordinary Android 14+ phone with an installed wallet. Saga is expected to work but its default wallet's behaviour is unverified by Solana Mobile itself, so it is not a tested target.
- Localnet: Surfpool (the Solana Foundation's drop-in replacement for `solana-test-validator`, and what `anchor test` runs by default since Anchor 1.0), forking mainnet: the SKR and ORE mints and any other mainnet account are fetched the first time a transaction touches them, so tests run against the real bytecode and account layouts with no clone script to keep current. It runs in clock mode (`block_production_mode = "clock"`, 200 ms slots), not Anchor's default transaction mode, because the draw's tests wait for a real slot window; the side effect, blockhashes that expire in real time as on mainnet, is wanted — it is what exposed and now pins the test transport's re-sign-on-expiry path. One quirk of Surfpool 1.6 to know: `getLatestBlockhash` at `confirmed` returns the hash of the slot it is still producing, which preflight can then report as "Blockhash not found" (Agave does not do this), so the tests fetch blockhashes at `finalized` — since 2026-10-23 the SDK's default, and the one commitment everything reads at (see the decisions log; on a Surfpool without the Alpenglow feature `finalized` trails the tip by 31 slots, which the private localnet avoids by starting it with `--feature A1pengvuM6JEcyNuTnMqepBKhwHE3N6PmUrdATGawhJS`; Surfpool 1.7.0, pinned since 2026-10-28, carries PR #876, the gate that makes the flag effective). The Entropy program is the one exception once the platform's own deployment exists: until it is on mainnet, tests load the fork's ELF — built from the pinned fork commit, checked in as a fixture with its hash, and rebuilt in CI to prove the two match — at `ENTROPY_PROGRAM` as an upgradeable-loader program, so the suite runs the bytecode that will be deployed; before that (the draw step itself) they ran against Regolith's deployed bytecode with `Var` accounts planted in the state `Open` leaves them in. Its cheatcodes are part of the test plan: `surfnet_timeTravel` and `surfnet_pauseClock` for the kickoff lock, the 30-day reclaim and the entropy sampling window; `surfnet_setTokenAccount` to give test wallets SKR and ORE without owning any; `surfnet_setAccount` to place a `Var` in any state (Entropy ships no IDL, so that one is raw bytes); `surfnet_registerIdl` with our own IDL and `surfnet_registerScenario` to set fields of our accounts by name (`pool.status`, `game.quarters_posted`) and to script a sequence of account states across slots, instead of hand-encoding bytes; `surfnet_profileTransaction` for compute-unit budgets. Mollusk (Anza's SVM harness, `mollusk-svm`; its releases track the Agave version we pin — 0.16.0 for 4.3.0) for Rust unit tests of single instructions and instruction chains, with the `Clock` and `SlotHashes` sysvars set directly — which is how the draw's sampling-window cases are tested exhaustively without waiting on a clock — and `mollusk-svm-bencher` for a compute-unit table (`compute_units.md`, committed, deltas shown per change) that the +20%/+30k wallet-headroom rule in DESIGN §10.4 is checked against. `@solana/kit-plugin-litesvm` for the SDK's own TypeScript unit tests, so neither suite needs a validator; Surfpool is for the end-to-end lifecycle. The full lifecycle (fill, draw, four settlements, return, split, suspended) must pass on Surfpool in CI before any mainnet deploy. The same Surfpool is what the Android app talks to in development, reached from the emulator or phone through the Solana Mobile CLI's `localnet` command, with Fake Wallet signing; that is why no devnet is needed for the app either.
- The cloud localnet (2026-10-21; dev only). The same Surfpool, run as one task in the dev scores cluster so that `dev.mybarpool.com`, the dev scores service and the dev keeper read one chain with the program on it — the end-to-end rehearsal of a game day before the first mainnet deploy, without a devnet (the rule above stands: it is a localnet that happens to run in the cloud, not a third environment). It runs `--offline` (no mainnet account is fetched: the Entropy fork is preloaded, the pools are SOL, SKR and ORE are disabled in its config) in clock mode at 200 ms, with its two ports as plain-HTTP listeners on the scores balancer; the browser reaches them through the CDN's `/rpc` and `/ws` as it would a provider, and the web build is the `local` profile with the hosted paths (`build:web:cloudnet`), so the cluster is `solana:localnet`, the faucet test wallet is offered, and the service path is used for everything the production build reads from the service. State is the task's memory: a restart is a reset, by design for now; the bootstrap (`services/localnet/src/cloudnet.ts`: both programs, airdrops, `initialize` with §3.1's initial column, the keeper's KMS address as score authority and provider) puts it back in seconds and `scores reindex` rebuilds the index. Surfpool's cheatcodes are reachable on `/rpc` like any method, which is what makes the bootstrap possible from an operator's machine and also why nothing of value may ever live on that chain. The prod stacks refuse the construct.
- Mainnet: the first deploy is the launch. The platform's Entropy deployment goes to mainnet before this program (same workflow, same multisig, verified against the fork), so the draw uses live Entropy from the first deploy; there is no test-mode stub. Program upgrade authority is the Squads multisig from the very first deploy.
